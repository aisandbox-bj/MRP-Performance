Version management · rollback-safe

Record of Change

Every push to aisandbox-bj/MRP-Performance is listed here: what changed, what it touched, and how to get back to the state before it. Before each push a backup/pre-<chunk> branch and a checkpoint/pre-<chunk> tag are cut at the current origin/main, and a local snapshot is kept in _rollback/<CHUNK>-pre/ beside the working folder. Entries marked dev are built and browser-verified but still waiting for the operator's off-repo validation.
How to roll back

Back to the state before any push

The working folder is not a git repository. Rollback always happens through a clone — never by running git init in the working folder. 

# Look at the state before a given push (read-only)
git clone https://github.com/aisandbox-bj/MRP-Performance.git peek
git -C peek checkout checkpoint/pre-v0.1.0     # or any checkpoint/pre-<chunk> tag

# Undo one pushed commit without rewriting history (preferred)
git -C peek checkout main
git -C peek revert <commit>
git -C peek push origin main

# Hard reset main to a checkpoint (history rewrite — only on an explicit decision)
git -C peek reset --hard checkpoint/pre-v0.1.0
git -C peek push --force-with-lease origin main

Borrowed Calibre Tune files are also kept exactly as copied (with their SHA-256 hashes) in _rollback/BORROWED-as-copied-from-tune-2896842/ next to the working folder, and listed in PROVENANCE.md in the repo.

v0.1.0 2026-09-25 dev

v0.1.0-dev — First build: a supply-chain performance workbench across every material — browser-verified; pending operator off-repo validation

  • What it is. A new Calibre app, separate from Calibre Tune and Trace. Where Tune and Trace start from one material, this starts from the process: every PR line, every receipt, every day of stock, for every material in the files. It answers how MRP responds, how long each leg of the chain takes, whether V1 parts are replenished to Max, and where the process deviates from plan — as distributions with both tails drill-able, never as a bare average.
  • Intake (PERF-INT). Calibre Tune's intake, copied and adapted. One assessment type — Supply-chain performance — needing MB51, the Inventory Master and PR History; the files decide the scope (every material with a movement or a PR line). New data-quality checks for PR History: need-by dates present, PR lines with a PO, POs that find a 107 / 109 receipt in MB51, blank sub-header rows, creation indicator present. The PR Delivery Date (need-by) is now read — it arrives as 20250608, which Tune's date reader silently turned into a blank. Three extra MB51 columns are read when present (value in local currency, entry date, storage location). A Calibre Tune dataset download also loads, and says so.
  • Engine (PERF-ENGINE). Follows every PR line PR → release → PO → 3PL (first 107) → site (first 109) → first use (first 261) with signed durations: an end dated before its start is kept and flagged “out of sequence”, not rounded to zero. Rebuilds each material's site stock for every day of the MB51 window from the Inventory Master snapshot, using the same movement-type signs as Tune. Parity check built in: on the June 2026 assessment all 2,351 chains match Trace's chain engine exactly and all 275 checked materials match Tune's stock back-calc on every day. Speed: that dataset builds in ~0.2 s; a 450,000-line MB51 / 70,000 PR-line / 9,930-material synthetic set in ~1.8 s.
  • Views (PERF-TRIGGER · PERF-LEGS · PERF-STOCK). Overview · Trigger → PR response · Exposure & stockouts · MRP cadence & quiet stretches · PR outcomes (real cancellations vs MRP churn, cancellation lag, open-PR ageing) · Internal (PR → PO, approval, buyer) · Supplier (by manufacturer) · 3PL (+ what's sitting at the 3PL) · End to end · Against plan (+ planned vs actual, process paths) · Order sizing (V1 order-to-Max, stock after receipt, reorder frequency) · Over / under (stock at receipt vs trigger line, $ over Max, shelf time) · Data checks & assumptions. Each distribution view: stat strip (closed, still open, out of sequence, P10 / median / P90 with “≥” when still-open items make it a lower bound), histogram, per-month boxes with % closed (months under 90% closed are provisional), a breakdown table and a drill table (bins, fast tail, slow tail, still open, out of sequence; CSV export).
  • Material segments (PERF-SEG). Drop-in tiles, dragged or clicked from a palette, ANDed together: movement, consumption events, consumption value, unit cost, stock value, stock on hand, material lead time, PR lines (each by quartile with the cut points shown, top / bottom %, or a range); manufacturer, MRP type, material group, purchasing group, stock status (pick values, include or exclude); material text; PR trigger (MRP / manual). Plus a time window (whole window, last 24 / 12 / 6 / 3 months, or custom months). Breakdown rows add themselves to the segment on click.
  • KPI targets. An empty target slot on every leg (⚙ Settings & targets). Once a target is entered the histogram and monthly boxes draw it and the view shows the share within target — left blank until the baseline is clear (operator decision).
  • Definitions that are decisions. 107 = arrived at the 3PL, 109 = received at site. Trigger line = Min (V1) or SS (PD). Cover = an open PO or goods at the 3PL; a PR alone is not cover. Cancelled = deletion flag + status N; MRP churn = MRP-created, no PO, cancelled within 2 days (Changed On as the cancel date). Blank creation indicator = unknown, not MRP. Manufacturer stands in for vendor. Min / Max / SS are today's values. POs open more than 365 days with no receipt are “stale”, not cover. All listed on the Data checks view.
  • Found while building — PD without safety stock. For PD parts with no SS, MRP raises a PR for demand (a reservation), not for low stock, and reservations aren't in these files. A first version counted every PD zero-stock day as “no PR yet”. Those events are now kept out of trigger response and trigger debt, named on the view with their own list, and still counted in stockouts. Same for V1 parts with Min 0.
  • Storage. Tune and this app are served from the same site (aisandbox-bj.github.io), and a browser keeps one storage per site. This app stores everything under its own mrpPerf namespace, never loads Tune's analyst-marks module and never writes Tune's keys; “Clear session data” only removes this app's data.
